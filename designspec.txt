# Electronics Pokédex — hybrid recognition design, v0.7

The future product helps engineering students learn about electronics. The
current milestone does not build that product. It tests a recognition pipeline
adapted from Caught in 4K: local catalog matching handles familiar devices and a
hosted multimodal vision API handles uncertain cases.

## Sequence

```text
CLIP catalog match
→ hosted vision API fallback when uncertain
→ evidence-based threshold, provider and model decision
→ application integration later
```

No application may present a device as recognized until an actual recognition
route has run and its response satisfies the fixed output contract. A model
response is evidence to evaluate, not ground truth.

## Fixed target contract

1. `laptop`
2. `desktop_computer_tower`
3. `monitor`
4. `printer`
5. `projector`

The model may also return `ambiguous`, `unsupported`, or `unreadable`. Exact
manufacturer, model, internal parts, material content and value are outside this
milestone.

## Adapted recognition architecture

Caught in 4K uses separate components for localization, catalog recognition and
unknown-item reasoning. This design preserves that separation while adapting it
to stationary electronics:

```mermaid
flowchart LR
    A[Selected device photo or crop] --> B[CLIP ViT-B/32]
    B --> C{Catalog score passes calibrated threshold?}
    C -->|Yes| D[Catalog family result]
    C -->|No| E[Hosted vision API]
    E --> F[Structured family result or abstention]
    D --> G[Result normalization]
    F --> G
    G --> H[Reviewed learning catalog]
```

- **CLIP catalog path:** OpenAI CLIP ViT-B/32 compares the device crop with
  frozen class descriptions and, when available, approved reference photos. It
  performs embedding comparison; it is not custom training.
- **Hosted API fallback:** one hosted multimodal model receives the selected crop
  and frozen five-class schema only when CLIP does not pass its calibrated
  threshold. It returns structured JSON or abstains.
- **Learning catalog:** the recognized family selects reviewed educational
  content. The vision model does not generate the published lesson.
- **Localization layer:** the photo experiment asks the user to center one
  device. Future room scanning adds an evaluated open-vocabulary or
  class-agnostic detector and tracker before CLIP. Caught in 4K's YOLO pose model
  finds people and hands; that exact proposal method does not apply to stationary
  campus devices.
- **Optional masks:** add a segmentation model such as FastSAM only if the
  interface requires object outlines. A detection box must not be presented as a
  mask.

Standard COCO YOLO weights directly support only `laptop` from this five-class
map. They are therefore unsuitable as the sole family recognizer.

## Bounded experiment

Compare two frozen routes on the same locked test manifest:

1. Hosted API for every image.
2. CLIP catalog first, with the same hosted API used only below the threshold.

This comparison measures whether the catalog path preserves recognition quality
while reducing API calls, latency and image disclosure. Tune the CLIP threshold
on development images and freeze it before the final test. Never tune from the
test results.

Keep both routes behind one recognition adapter:

```python
recognize(image, allowed_classes) -> RecognitionResult
```

The CLIP checkpoint, catalog descriptions, reference gallery, similarity rule,
threshold, API provider and API model ID must be frozen before the final run and
recorded with every prediction. Changing any of them creates a new experiment
version. API credentials remain on the backend and must never be included in
logs or client code.

This experiment performs whole-image device-family recognition. It does not prove
localization, detection, segmentation or continuous-video performance. If the
photo contains several plausible primary devices, the correct response is
`ambiguous` rather than an invented bounding box or arbitrary selection.

## Response contract

Each successful response normalizes to:

```json
{
  "outcome": "laptop",
  "source": "clip_catalog",
  "score": 0.31,
  "evidence": null
}
```

`source` is `clip_catalog` or `hosted_api`. `outcome` must be one of the five
classes or three abstention outcomes. A score retains the producing model's raw
similarity or confidence value and is not presented as a probability. CLIP does
not generate visual reasoning, so its evidence is null. Hosted evidence is a
short observable reason and must not contain unverified brand, model or
internal-component claims. Invalid JSON, an unknown outcome, timeout, rate limit
or provider error is a request failure; it must not be converted to `unsupported`
or counted as a correct abstention.

## Reproducibility contract

Each prediction record preserves:

- image ID and SHA-256, without ground truth in the model request;
- provider, exact model ID and API version when the hosted route runs, plus the
  adapter version for every record;
- CLIP checkpoint identifier and hash, catalog version, gallery manifest,
  similarity rule and frozen threshold;
- selected route, CLIP candidates and raw similarity scores;
- prompt and response-schema versions;
- image dimensions and preprocessing settings;
- request parameters that affect model behavior;
- start time, elapsed time, provider request ID when returned, and explicit error;
- normalized outcome and preserved raw response with secrets removed.

The runner writes predictions atomically and retains one record for every
manifest row, including failures. Filenames provide file locations only and
never determine predictions.

## Evaluation inputs

Use 10–20 permitted photos per target class and 20–30 confusing or unsupported
examples only after collection is approved. Include multiple physical devices,
viewpoints, lighting conditions, distances, occlusions, clutter and empty scenes.
Group related images by physical device and capture session so they cannot leak
between splits. Reference-gallery images come only from development devices; do
not enroll the physical devices reserved for the final test. Lock the final test
manifest before model requests begin.

Report each route separately and end to end: per-class precision and recall, the
complete confusion matrix, abstention rate, unsupported-object false acceptance,
API fallback rate, request failures, and median and p95 latency. Also report API
requests avoided without treating avoidance as success. Preserve representative
errors and raw responses. Do not report boxes, masks or localization metrics for
this whole-image experiment.

## Later room-scanning path

When the product requires live boxes, run localization and tracking on device or
at the edge, retain the best crop per track, then send that crop through the same
CLIP/API cascade. Evaluate an open-vocabulary detector against all five classes
before selecting it. Do not send every video frame to the hosted API. Local
Qwen3-VL through Ollama remains an unevaluated offline fallback and is outside
the current experiment.

## Privacy and cost controls

- Tell participants that selected photos leave the application backend for the
  configured vision provider.
- Record the provider's retention and training-data terms before sending images.
- Send selected device photos, not continuous video or unrelated frames.
- Remove images after evaluation according to the approved retention plan.
- Set an experiment request limit and cost ceiling before enabling paid calls.
- Retry only transient failures and cap retries so one image cannot spend without
  bound.

## Stop conditions

This specification change does not enable a paid service, download CLIP weights,
or authorize reading credentials. If an approved provider, model ID, credentials, request limit,
retention terms or permitted images are absent, produce the adapter, schema,
tests and blocker report, then stop before making a request. Do not install local
model runtimes, download weights, train models, collect a large dataset or change
global configuration for this milestone.

## Later application milestone

Only after an evidence-based model decision may a separate application milestone
add photo capture, educational cards, corrections and saved collections. Its UI
must distinguish model predictions, user corrections, abstentions and request
failures without presenting guesses as verified recognition.
