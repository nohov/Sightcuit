# Electronics Pokédex — technical design specification, v0.8

This design adopts the general recognition flow used by Caught in 4K. A fast
local vision path finds and tracks an object, OpenAI CLIP ViT-B/32 identifies
known catalog entries, and a hosted vision-language model handles uncertain
objects. The application then opens reviewed educational content for the
identified device family.

The product supports these five device families first:

1. `laptop`
2. `desktop_computer_tower`
3. `monitor`
4. `printer`
5. `projector`

It may also return `ambiguous`, `unsupported`, or `unreadable`. Brand, exact
model, internal parts, material content and value require later evidence and are
not inferred from a family result.

## 1. Model stack

| Role | Initial model or component | Purpose |
| --- | --- | --- |
| Device proposals | YOLO-World v2 with the five device prompts | Find candidate electronics in room frames |
| Person-carried mode | YOLO11n-pose | Use wrists and hands to crop a device someone is carrying |
| Tracking | ByteTrack through Ultralytics | Keep one track ID across frames and suppress duplicate discoveries |
| Primary identification | OpenAI CLIP ViT-B/32 | Compare a device crop with catalog text and reference-image embeddings |
| Uncertain-item fallback | Hosted multimodal vision API | Classify or abstain when CLIP does not pass its calibrated threshold |
| Optional outline | FastSAM | Produce a mask when the interface needs an outline rather than a box |
| Product knowledge | Reviewed learning catalog | Supply the engineering explanation shown to students |

CLIP ViT-B/32 is the primary recognition model, matching Caught in 4K. This is
embedding comparison, not custom model training. The hosted API is a fallback,
not the default request for every frame.

Caught in 4K uses YOLO11n-pose because its item is usually in a person's hand.
That same model is useful only for our person-carried scan mode. A room scan also
needs proposals for stationary devices, so the initial design uses the
promptable YOLO-World path already supported in their worker. Both proposal
modes feed the same CLIP catalog.

Standard COCO YOLO weights are not the device-family classifier. Their built-in
labels directly cover only `laptop` from the five-class map and must not silently
map `tv` to `monitor`.

## 2. End-to-end flow

```mermaid
flowchart LR
    A[Camera frames] --> B[Device proposals]
    B --> C[ByteTrack tracks]
    C --> D[Best crop per track]
    D --> E[CLIP ViT-B/32]
    E --> F{Catalog threshold passed?}
    F -->|Yes| G[Catalog family]
    F -->|No| H[Hosted vision API]
    H --> I[Family or abstention]
    G --> J[Normalize result]
    I --> J
    J --> K[Reviewed learning card]
    J --> L[Red box or optional mask]
```

Runtime behavior:

1. The camera supplies frames to the selected proposal mode.
2. ByteTrack groups repeated boxes into a stable track.
3. The client or edge worker retains several clear crops and selects the best
   crop using size, sharpness, visibility and proposal confidence.
4. CLIP embeds that crop and compares it with the frozen catalog gallery.
5. A catalog result is accepted only if its score and separation from the
   runner-up satisfy thresholds frozen on development data.
6. An uncertain track sends its best face-free device crops to the hosted API
   once. Continuous video and unrelated full frames are not API inputs.
7. The backend validates the structured result, retrieves the reviewed learning
   card and returns the result to the client.
8. The tracker reuses that answer while the object remains in view, preventing
   repeated API calls and duplicate Pokédex entries.

The first implementation may run this flow on a captured photo with one centered
device. The room-scanning version activates proposals, tracking and duplicate
suppression without changing the recognition contract.

## 3. CLIP catalog and enrollment

The catalog contains one versioned entry per supported family:

```json
{
  "family": "projector",
  "descriptions": [
    "a classroom digital projector",
    "an electronic projector that casts an image onto a screen"
  ],
  "reference_images": [
    "catalog/projector/reference-001.jpg"
  ]
}
```

At catalog build time, CLIP ViT-B/32 embeds the descriptions and approved
reference images. At recognition time, it embeds only the selected crop and
compares normalized vectors with cosine similarity. Store the gallery version,
CLIP checkpoint hash, preprocessing version and source record for every
embedding.

Reference enrollment improves the catalog without retraining CLIP. Enrollment
images must be reviewed, cover different physical devices and viewpoints, and
remain separate from final test devices. Adding an image or changing wording
creates a new catalog version and requires reevaluation.

## 4. Hosted API fallback

The fallback receives one to several selected device crops and the fixed class
definitions. It must return JSON matching the response schema. The exact
provider and model ID are configuration frozen for each evaluation or release.

```json
{
  "status": "identified",
  "family": "projector",
  "evidence": "A projection lens and ceiling-mount body are visible."
}
```

Allowed statuses are `identified`, `ambiguous`, `unsupported`, and `unreadable`.
An identified response must use one of the five family IDs. Invalid JSON,
unknown labels, timeouts, rate limits and provider failures are request failures;
they are not converted into `unsupported` results.

Keep API credentials on the backend. Record provider, exact model ID, prompt
version, response-schema version, latency, provider request ID when returned,
normalized result and the raw response with secrets removed.

## 5. Recognition result contract

```typescript
type RecognitionResult = {
  trackId: string | null;
  status: "identified" | "ambiguous" | "unsupported" | "unreadable";
  family: "laptop" | "desktop_computer_tower" | "monitor" | "printer" | "projector" | null;
  source: "clip_catalog" | "hosted_api";
  score: number | null;
  candidates: Array<{ family: string; score: number | null }>;
  box: [number, number, number, number] | null;
  mask: Array<[number, number]> | null;
  modelVersions: Record<string, string>;
  catalogVersion: string;
};
```

CLIP similarity and detector confidence are retained with their origin. Neither
is displayed as a calibrated probability unless calibration has been measured.
A box is never presented as a segmentation mask. Whole-image API classification
without coordinates does not create a box.

## 6. Learning layer

Recognition selects a reviewed family-level learning card. The card explains:

- what the device does;
- its typical inputs and outputs;
- its operating process;
- typical major components and their functions;
- relevant engineering concepts;
- an observation activity and comprehension question;
- sources and content revision.

The hosted vision model does not write published learning content during a scan.
If no approved card exists, the interface reports that educational coverage is
pending. A user correction changes the selected family only after confirmation
and is preserved as feedback rather than rewritten as the model prediction.

## 7. Evaluation

Use the same locked manifests to compare:

1. CLIP text descriptions only.
2. CLIP text plus reference-image enrollment.
3. Hosted API only.
4. The complete CLIP-first/API-fallback cascade.

Tune proposal, CLIP acceptance and runner-up separation thresholds using
development devices only. Keep physical devices, capture sessions and locations
separate across development and final test sets. Include all five classes,
multiple devices and viewpoints, confusing electronics and empty scenes.

Report:

- proposal recall and false proposals for room scanning;
- per-class recognition precision and recall;
- complete confusion matrix and abstention rate;
- unsupported-object false acceptance;
- CLIP acceptance and API fallback rates;
- duplicate discoveries per physical object;
- median and p95 latency by stage;
- hosted requests and estimated cost per accepted result;
- box quality and mask quality only when those outputs actually run.

Preserve raw proposals, CLIP candidates and similarities, API responses, final
predictions, commands, model versions and representative failures. An API call
avoided is a cost result, not an accuracy success.

## 8. Privacy and operations

- Process localization, tracking and CLIP locally or at the edge when the target
  hardware can support them.
- Send only selected device crops to the hosted provider.
- Document the provider's image-retention and model-training terms.
- Keep faces and unrelated people out of API crops; reject a crop if redaction
  cannot be verified.
- Set request, retry and spending limits before enabling the hosted path.
- Cache a fallback answer by track and image hash for the active session.
- Treat saving a discovery and donating an image to a dataset as separate user
  choices.

## 9. Implementation order

1. Build and test the CLIP catalog on captured single-device photos.
2. Add the structured hosted API fallback and compare the four evaluation routes.
3. Add YOLO-World proposals and ByteTrack for room video.
4. Add optional FastSAM masks only if boxes are insufficient for the interface.
5. Connect recognized families to approved learning cards.
6. Run an unseen-campus walkthrough and lock the release report.

This specification does not itself enable a paid service, download model weights
or authorize reading credentials. Record licenses, exact artifacts, provider
terms and costs before implementation. Do not claim accuracy, latency or mobile
performance until logs from the target hardware exist.
